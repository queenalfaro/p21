## 1. Главный принцип: качество В РАМКАХ проекта (анти-оверинжиниринг)

Это важнейший принцип. Нарушать его так же плохо, как писать грязный код.

- Tech lead — не тот, кто кладёт в проект всё, что бывает в больших системах. Это тот, кто под **конкретную** задачу собирает **минимально достаточное и корректное** решение.
- **Качество** = корректно, надёжно, читаемо, поддерживаемо, идиоматично. Качество ≠ «максимально навороченно».
- Каждый слой, абстракция, библиотека, паттерн, конфиг и доп. доку **обязан** закрывать реальную **текущую** потребность из ТЗ. Нет потребности — нет решения.
- На развилке «проще vs сложнее, оба корректны» — выбирай **проще**.
- **Запрещено:** спекулятивная обобщённость, инфраструктура «на всякий случай», паттерны без текущей проблемы, абстракции ради абстракций, лишние зависимости, преждевременная оптимизация.
- **Тест на нужность** (применяй к каждому нетривиальному решению): _«Какое требование ТЗ это закрывает? Что конкретно сломается, если не делать этого сейчас?»_ Нет внятного ответа → не делать. Сомневаешься → спроси.
- Этот принцип распространяется и на сам процесс: не плоди лишних доков, обёрток, конфигов и церемоний.

**Конкретно для этого проекта:**

| ДА (нужно)                                                          | НЕТ (оверинжиниринг для этого проекта)                |
| ------------------------------------------------------------------- | ----------------------------------------------------- |
| Полиморфизм сообщений через слот/render-props (см. §5)              | Плагинная система/реестр типов сообщений «на будущее» |
| Zustand для UI-состояния как есть                                   | Свой слой-обёртка/абстракция над Zustand              |
| 2 роли + массив `permissions` с `can()` (по ТЗ)                     | Полноценный RBAC-движок с иерархиями ролей            |
| Тесты на чистую критичную логику (Decision Engine, утилиты времени) | Погоня за 100% покрытием, e2e на каждый клик          |
| React Query + Supabase Realtime                                     | Своя event-bus/CQRS-инфраструктура поверх             |
| Заложить **швы** под push (см. §5)                                  | Полная реализация FCM сейчас (это последняя фаза)     |

## 3. Рабочий процесс: фазы + согласование (ГЛАВНОЕ)

Процесс жёсткий и пошаговый. Согласование — это **жёсткий стоп**, а не формальность. Не продолжай «по инерции».

### Фаза 0 — Discovery (без кода фич)

1. Прочитай **все** файлы `/docs`.
2. Изучи окружение: `.devcontainer/`, существующие конфиги, `package.json`. **Среду не трогай** — она готова (WSL2 → Docker → devcontainers). Только понять, не менять.
3. Изучи SQL-схему из `supabase.md` (сущности, связи, RPC, cron, `UNLOGGED`-таблицы аналитики).
4. Создай:
    - `docs/UNDERSTANDING.md` — как ты понял продукт, ключевые сущности и потоки, **список открытых вопросов ко мне**.
    - `docs/ROADMAP.md` — **полный** поэтапный план на весь ТЗ (чтобы потом не было дыр).
5. **СТОП.** Жди явного «согласовано» по ROADMAP. Без этого — никакого кода фич.

**Формат каждой фазы в ROADMAP** (обязателен, иначе план неполный):

- **Цель** — что и зачем.
- **Скоуп** — что входит (конкретные экраны/фичи/слайсы).
- **Зависимости** — от каких фаз/решений зависит.
- **Артефакты** — что появится в репозитории.
- **Критерии приёмки (DoD)** — проверяемый список «готово, если…».
- **Что НЕ входит** — явная граница, чтобы не расползалось.

Рекомендуемый порядок фаз (предложи свой, но логика такая): каркас+тулинг → shared (Supabase-клиент, UI-кит) → entities (типы/схемы) → MVP чата (лента + realtime) → типы сообщений (опрос/чеклист/оценка) → комнаты/вступление/QR/share → профиль/анонимный вход → админ-зона (управление + splitscreen) → дашборд аналитики (графики) → **фоновая аналитика (`processes`)** → **push (FCM)**. Аналитику и push — в конце: они скрыты/последние по ТЗ и не должны блокировать основной флоу.

### Цикл по каждой фазе

1. **Перескажи** цель фазы и критерии приёмки (из ROADMAP). Если по ходу выяснилось, что план нужно поправить — синхронизируй ROADMAP и спроси, **прежде чем** отклоняться.
2. **Реализуй.** Маленькие осмысленные коммиты (Conventional Commits).
3. **Самопроверка** перед отчётом: против ТЗ · против §1 (нет ли оверинжиниринга) · против FSD (§4) · против DoD (§7). Прогони критерии приёмки руками.
4. **Отчёт** (кратко, по делу): что сделано · как проверить (команды/шаги) · отклонения и принятые решения · открытые вопросы.
5. **СТОП.** Жди sign-off перед следующей фазой. **Никогда** не начинай следующую фазу без согласования и **не расширяй скоуп молча.**

Если фаза оказалась больше, чем казалось — **раздели её и предупреди**, не тащи всё разом. Помни о финальной цели на каждом шаге; если ловишь себя на отклонении от ТЗ — вернись к `/docs` или спроси.

## 4. Архитектура: строгий FSD

Золотая архитектура важнее упрощений — **но в рамках проекта**: без явно лишних слоёв и слайсов.

- **Иерархия слоёв (сверху вниз):** `app` → `processes` → `pages` → `widgets` → `features` → `entities` → `shared`. Верхние импортируют нижние, **никогда** наоборот.
- **Раскладка слайсов внутри слоёв — строго по `arch.md`** (это источник истины по структуре, не дублирую здесь).
- **Без cross-import** между слайсами одного слоя — только через публичный API.
- **Публичный API:** каждый слайс экспортит наружу через `index.ts`; снаружи импортируем только из него, не лезем во внутренности (`model/`, `ui/`, `api/`) напрямую.
- **Не создавай пустые слои/слайсы впрок.** Слайс появляется, когда есть реальная сущность/фича из ТЗ.
- **Линтер границ обязателен:** настрой ESLint-правило, запрещающее нарушения FSD (`eslint-plugin-boundaries` или `import/no-restricted-paths`). Нарушение границ = баг, а не стилистика.

## 5. Доменные правила проекта (не нарушать)

- **UX/UI — паритет с Telegram:** паттерны, расположение кнопок, поведение копируют Telegram в аналогичных функциях. Качественно, **без «нейрослопа»**. Вёрстка **android-first** (мобильный экран); desktop/iOS — рабочие, но **без отдельного дизайна** (на desktop — один мобильный экран по центру, как Telegram Web).
- **Лента — ядро.** Все активности (опросы, оценки, системные уведомления) — это **кастомные сообщения в общей ленте**, не отдельные страницы.
- **Полиморфизм сообщений — паттерн «слот»/render-props:** `entities/message/ui/MessageCard` рендерит общий баббл + `contentSlot`, а конкретный контент (текст/опрос/чеклист/оценка) подставляет `widgets/chat-feed` из фич. **Никакого разрастающегося `switch/case`.**
- **Чат:** виртуализация через `react-virtuoso`; realtime через **Supabase Realtime**; подписки обновляют/инвалидируют кэш **TanStack Query** (Server State и UI State разделены жёстко, см. §6).
- **Треды:** пока только reply через `parent_id`. Отдельной сущности «топик» нет (по ТЗ).
- **Идентификация:** **без Supabase Auth.** Кастомная анонимная модель: вход по имени → апгрейд до полного профиля (username, аватар). Без email/телефона/OAuth. RLS на dev отключён — **не воюй с этим**.
- **Аналитика НИКОГДА не тормозит UI** (приоритет приложения выше статистики):
    - Живёт в `processes/background-analytics`, подключается на уровне рутового layout, работает скрыто.
    - In-memory очередь событий — **обычный массив, НЕ Zustand** (чтобы не триггерить ререндеры).
    - **Web Worker heartbeat**, батч-отправка раз в N секунд, `navigator.sendBeacon` на `pagehide`.
    - Приёмы фонового удержания вкладки (worker, аудио-трюк) — строго по `userless.md` / `arch.md`.
    - **`adminview` НЕ отправляет аналитику.**
- **Decision Engine — чистая функция** (вход: состояние сигналов → выход: статус `ENGAGED`/`DISTRACTED`/`UNKNOWN` + reason). Правила и `keep_last` — строго по таблицам из `userless.md`, порядок правил соблюдать (первое совпадение выигрывает). Изолирован и покрыт юнит-тестами.
- **Графики дашборда:** агрегация бакетами на **сервере** (`analytics_timeline` + cron-snapshot из схемы); клиент не рендерит сырьё за часы. Таймлайн — от перехода комнаты в `active`, без обрезки; интерактив (hover-значения, подсветка точек кастомных сообщений, клик → сводка) — по `adminview.md`.
- **Раскладка ролей:** на desktop у админа — динамический splitscreen (управление | чат | аналитика, сворачиваемые/раскрываемые); на телефоне splitscreen нет — чат + управление в шапке + кнопка статистики (отдельные страницы). По `adminview.md`. На странице комнаты права проверяются в `pages/room` (`entities/user`).
- **Push (FCM) — последняя фаза.** Сейчас только **заложить чистые швы** в архитектуре (`features/push-notifications`, кастомный SW через `injectManifest`), не реализовывать целиком.

## 6. Стек и версии (актуальность критична)

Стек **фиксирован ТЗ** (`stack.md`) — не подменяй библиотеки без согласования:

> Vite · React 19 · React Router v7 · TypeScript · Tailwind v4 · shadcn/ui · TanStack Query v5 + Supabase JS · Zustand · React Hook Form + Zod · react-virtuoso · vite-plugin-pwa + Workbox (`workbox-background-sync`) · FCM (push) · Supabase Edge Functions (триггер push). Прод: Supabase + Cloudflare Pages.

**State management — разделять жёстко:** Server State (сообщения, комнаты, профиль) → TanStack Query + Supabase. UI State (шторки, режим splitscreen) → Zustand. Формы → React Hook Form + Zod. In-memory батчи аналитики → обычный массив (см. §5).

**Версии:** перед установкой **проверь актуальные стабильные версии и известные несовместимости** (web/официальная дока). **Пини точные версии** в `package.json`. Зафиксируй выбранные версии и острые углы в `docs/DECISIONS.md`. **Не хардкодь номера версий в этом файле** — он живёт долго.

**Острые углы (на момент написания — перепроверь актуальность):**

- **Tailwind v4 на Vite** → плагин `@tailwindcss/vite` + CSS-first конфиг (`@theme` в css), цвета OKLCH. Без PostCSS-флоу и без `tailwind.config.js`-центрированной настройки из v3.
- **shadcn/ui** уже поддерживает Tailwind v4 + React 19. Инициализация: `npx shadcn@latest init` (стиль `new-york`, `data-slot`-атрибуты). Тосты — `sonner` (не deprecated `toast`). Компоненты живут в `shared/ui` (это часть FSD-shared).
- **React Router v7** → пакет `react-router` (НЕ `react-router-dom`). Режим — **declarative** (или **data**, если нужны лоадеры), **НЕ framework/SSR**: приложение — клиентский **SPA + PWA на статике** Cloudflare Pages.
- **vite-plugin-pwa** → для кастомного SW (понадобится под FCM) используем `strategies: 'injectManifest'`; dev-режим через `devOptions`. Workbox 7.x.

## 7. Definition of Done (что значит «production-ready» здесь)

Фаза не «готова», пока всё это не выполнено:

- TypeScript **strict**, без `any` (исключения — обоснованы и помечены комментарием).
- **ESLint + Prettier** чисто; правила границ FSD проходят; в проде нет ошибок/ворнингов в консоли.
- Все сетевые/realtime-состояния обрабатывают **loading / empty / error**. Подписки, таймеры и воркеры корректно **очищаются** (нет утечек).
- Границы данных (вход из сети и форм) валидируются **Zod**.
- **Доступность по-базовому:** примитивы Radix/shadcn используются правильно (фокус, клавиатура, aria). Без отдельного a11y-проекта, но корректно.
- **PWA:** устанавливается, оффлайн-оболочка работает, корректный флоу обновления SW.
- **Производительность ленты:** виртуализация работает на длинной истории без тормозов.
- **Тесты — прагматично (Vitest):** покрываем чистую критичную логику (Decision Engine; утилиты времени/бакетов; мапперы payload), а не гонимся за покрытием UI. RTL — только для нетривиальных компонентов.
- Перед отчётом — ручной прогон по критериям приёмки фазы.
